# 合成大奶娃 · AI 自动打（BigNaiWa Bot）

给 [合成大奶娃 v1](https://yhsome.github.io/BigNaiWa/v1/) 写的一个自动打手：
**把游戏的物理引擎 1:1 移植出来当年仿真模型**，每次出手前把 40+ 个落点各推演一遍，
按「拿到的分 + 盘面风险 + 后续合成机会」挑一个最稳的落点丢下去。

- 移植引擎与线上物理**逐帧零偏差**（`tools/verify-engine.mjs`：1620 帧 / 53 次投放，最大坐标偏差 0.00e+0 px，分数与球数完全一致）
- 决策管线：候选生成 → 精确推演 → 特征评估 → 精选长推演 → 两层搜索（下一颗水果是已知的）→ 局部细化
- **推演跑在 Web Worker 里**，主线程实测 8.3 ms/帧 —— 页面完全不卡（v1 是同步算，会僵住）
- 页面右上角（可拖动）有**灵动岛控制台**：暂停 / 实时·快进 / 排行榜开关 / 自动复活 / 搜索强度
- 一局打完**点重开它会自己接着打**；关闭脚本会把游戏交还给你，页面照常能玩
- 实测：浏览器里全自动单局 **4357 分**，合出最大的「神奶蛙」，用了 2 枚复活币（详见「成绩」一节）

## 一、怎么用

### 1. 最简单：控制台粘贴

1. 打开 <https://yhsome.github.io/BigNaiWa/v1/>
2. F12 → Console → 粘贴 [`dist/naiwa-bot.js`](dist/naiwa-bot.js) 的全部内容 → 回车
3. 开打：

```js
NaiwaBot.run()                                  // 实时模式：跟着游戏节奏打，可以边看边玩
NaiwaBot.run({ mode: 'turbo' })                 // 快进模式：自己驱动时钟，刷分快得多
NaiwaBot.run({ strength: 'deep' })              // 想更强就加搜索深度（fast / normal / deep）
```

开起来之后，右上角那颗小胶囊（🍉 分数 + 状态灯）就是控制台：**点一下展开**，
里面能暂停、切模式、切搜索强度、改「投掷时机」策略、开关排行榜提交与自动复活。
胶囊可以**拖着换位置**。

常用命令：

```js
const b = window.__NAIWA_BOT__;
b.stop()                     // 关掉 AI（游戏交回给你，页面照常能玩）
b.setPaused(true)            // 暂停（连游戏一起冻住）
b.setMode('turbo')           // 运行时切模式
b.restartGame()              // 重开一局，AI 继续
b.stats                      // 分数、决策耗时、投掷时机分布…
```

### 2. 油猴脚本

安装 [`dist/naiwa-bot.user.js`](dist/naiwa-bot.user.js)，打开游戏页会看到 `[合成大奶娃 bot] 已装载`，
然后在控制台敲 `NaiwaBot.run()` 即可（脚本里默认不自动开打）。

### 3. 无人值守跑分（Edge headless）

```bash
cd BigNaiWa-bot
node tools/live.mjs --mode turbo --secs 600 --shots 1        # 本地离线副本跑一局
node tools/live.mjs --url https://yhsome.github.io/BigNaiWa/v1/   # 打线上页面
```

### 4. 自我对弈 / 调参（不开浏览器，纯 Node）

```bash
node tools/selfplay.mjs --games 5 --seed 1                         # 5 局，打印分数
node tools/tune.mjs --configs out/configs-ablation.json --games 10 --workers 8   # 并行对照实验
node tools/verify-engine.mjs                                       # 校验移植引擎 = 线上物理
```

> ⚠️ **排行榜**：游戏结算时 `leaderboard.min.js` 会把成绩**自动提交到公开排行榜**。
> bot 默认把这次提交拦下来（`blockLeaderboard: true`），免得刷榜打扰别人；
> 想上榜就在灵动岛里点「允许上榜」，或者 `NaiwaBot.run({ blockLeaderboard: false })`。
> 跑分脚本 `live.mjs` 也会直接拦掉排行榜脚本。

## 二、这台游戏机是怎么运转的（从 game.js 里读出来的机制）

| 项目 | 数值 |
| --- | --- |
| 逻辑画布 / 墙厚 | 420 × 700，左右墙 10px |
| 投放高度 / 警戒线 | y=74 / y=142 |
| 重力 / 固定步长 | 2600 px/s²，主循环 `update(1/60)`，每帧 3 子步 × 6 次约束迭代 |
| 水果半径 | 17 23 31 39 48 58 69 81 94 108 124（共 11 级） |
| 碰撞体 | 每颗水果 16 个小圆（贴图轮廓，`parts.js`），不是圆 |
| 合成得分 | 合出第 n 级得 `[0,1,3,6,10,15,21,28,36,45,55][n]`（三角数） |
| 新水果 | 只掉 0–4 级，权重 0.28/0.24/0.20/0.16/0.12，且和「当前这颗」不同 |
| 神奶蛙 × 2 | 一起炸掉，+500 分 + 1 枚复活币（唯一的泄压阀） |
| 判负 | 有水果顶到 y<142 **且速度 <140 持续 1.5 秒** |
| 复活币 | 每 2000 分发一枚；复活 = 删掉最顶上那颗 + 清掉警戒线以上全部 |
| 投放节奏 | 两次投放最小间隔 360ms |

引擎还暴露了一个调试句柄 `window.__DNW__`（`state / tryDrop / update / render / FRUITS / makeBall …`），
移植引擎就是对着它做的状态搬运与对照 —— 这也让「读状态」和「出手」都非常干净。

## 三、算法

### 3.1 核心：用游戏自己的物理做「假设落点」推演

最朴素的高分打法就是「丢下去之前先想一下」。难点在于**想得准**：

1. `src/engine.js` 把 game.js 里的 `stepPhysics / processMerges / checkGameOver / update / tryDrop`
   逐行照抄（同样的常量、同样的运算顺序、同样的 `Float32Array` 精度），只砍掉粒子、音效、DOM。
2. 把当前盘面搬进移植引擎（`adoptFromGame`），对每个候选落点：克隆世界 → 投放 → 固定步长跑到稳定。
3. 「克隆世界 + 跑物理」不碰真实游戏，所以推演多少遍都不影响正在进行的对局。

**保真度**：`tools/verify-engine.mjs` 在同一个浏览器进程里先跑真实游戏 1200 帧、
再用移植引擎重放同样 1200 帧，逐帧比对每颗水果的坐标 —— 结果 dx=dy=0.00e+0、分数与球数完全一致。

> 为什么不用「便宜的近似模型」来加速？`tools/model-agreement.mjs` 做了对照实验：
> 把 16 个小圆砍成 8/4/2 个、或者直接退化成圆，推演快了 20–50 倍，
> 但**排序和精确物理几乎不相关**（Spearman ρ≈0，top1 命中率 0–13%）。
> 原因是「这颗到底会不会碰到、会不会合」本来就是混沌的，模型一糙，预测就变成噪声。
> 结论：决策必须用精确物理，加速只能从「少推几次」「推短一点」「多核并行」上找。

### 3.2 决策管线（`src/planner.js`）

```
① 候选生成   可投范围 [WALL+r, W-WALL-r] 内按 step=8px 均分 ≈ 45 个落点
② 粗筛推演   每个候选投放后跑 1.2s（提前稳定就收工），算评估值
③ 精选       前 8 名再跑 2.6s 长推演（有些连锁合成要 1.5s 后才发生）
④ 期望搜索   下一颗水果是随机的：前 3 名 × {5 种可能水果} × 各自最优应对，按掉落权重取期望
⑤ 局部细化   冠军落点左右 ±8px 再试 4 个更细的位置
```

### 3.3 评估函数

推演结束后的盘面用一组归一化特征打分（权重可调、可用 `tools/tune.mjs` 做对照实验）：

| 特征 | 含义 | 方向 |
| --- | --- | --- |
| `merge` / `mergeW` | 推演窗口内真实拿到的分 / 合出的最大等级 | ＋ |
| `top` | 堆顶逼近警戒线的二次惩罚 | － |
| `above` | 越线水果数量 × 体积 | － |
| `overT` | 越线计时（离判负还有多远） | － |
| `bump` | 表面起伏（8 条竖条的顶高差） | － |
| `adj` | 同级相邻度（距离越近越可能马上合） | ＋ |
| `bigPair` | **同级大果抱团**：两只半奶蛙/神奶蛙挨着 → 大赚，分居两地 → 重罚 | ＋ |
| `blocked` | **两只大果之间塞着别的水果**（合不拢的直接原因） | － |
| `mono` | 层级沿水平方向的梯度（大果归边，默认关，可调参开） | ＋ |
| `bigHigh` | 大果被顶到高处 | － |
| `buried` | 大果压在小果上（被埋的小果就废了） | － |
| `frag` | 碎块惩罚 | － |
| `dead` | 推演中判负（手里没币时一票否决） | — |

### 3.4 投掷时机：现在丢，还是等这一波合成安静下来再丢？

这是用户提的真问题：合成的一瞬间棋盘是乱的（水果在弹、在滚、连锁还没走完）。

现在的做法是**把时机也交给搜索**。盘面还在动的时候，规划器会算两遍、拿同一个评估函数比：

```
① 现在丢   从当前（还在动的）盘面推演 → 最优落点 a 的价值 V_now
② 等它安静 让棋盘自己跑到静止（最多 3 秒），再推演 → 最优落点 b 的价值 V_later
           （等待期间自己合出来的分也算进 V_later）
选 V 更高的那个；等待还有一点点「时间惩罚」用来打破平局。
如果光等着就输了（越线判负），直接选①。
```

推演里「丢进混乱中会发生什么」是能算准的 —— 因为那正是线上物理本身，
所以 bot 甚至能借势把水果撞进旁边的空档；这一点人类玩家做不到。

### 3.5 把复活币当资源花（用户明确要求）

复活币 = 每 2000 分一枚 + 两只神奶蛙相撞再送一枚。用户说「分越高越好，允许用币换空间」，
所以：

- **推演里允许用币续命**：一条路线如果半路越线，但手里有币，推演不会判它死，
  而是就地做一次复活（清掉警戒线以上、删掉最顶上那颗）再继续跑到底 ——
  于是「堆到顶→清一片→接着合」这种打法会被算成一笔有代价但可接受的买卖。
- **风险项缩放**：手里有币时，`top`/`above`/`overT` 这几个风险权重 × 0.45，
  允许把场面堆得更高，换取更大的合成空间。
- 灵动岛里可以一键切成「不用复活币」，自己对比两种打法。

### 3.6 后期「大果永远合不到一起」的专项治理

后期最常见的死法不是被顶死，而是**两只大奶蛙各占一边、中间塞着一堆小果**，
谁也动不了谁，最后只能在上面继续堆到爆。为此加了两项特征：

- `bigPair`：同级大果之间的距离打分（权重随 tier 超线性增长 `(tier-3)^1.6`），
  挨着 = 马上能合 = 大赚；分居两侧 = 基本等于废了 = 重罚。
- `blocked`：两只同级大果的**水平连线之间**、位置更高的水果，就是挡住它们的东西，按 tier 加权扣分。

效果就是 bot 会更愿意「先在大果旁边腾出位置、把小果往别处丢」，而不是随便找个浅坑就丢。

### 3.7 推演里到底算了什么？（以及游戏里根本不存在的东西）

两个常见疑问，这里用代码 + 实测数据回答：

**① 落下的这颗对场上其它水果的影响，算了吗？**
算了 —— 而且不是「估算」，是把**线上同一套物理**整段往前推：落子会和每一颗水果真实碰撞、推挤、滚动，
被推动的水果又可能触发别处的合成。所有候选落点的评分都来自这个前推结果。
实测（`tools/impact-probe.mjs`，4 个中后期盘面 × 89 个候选落点）：

```
落子一共触发合成 24 次
  · 落子本体直接合成  16 次（67%）
  · 连锁合成(gen>=1)   8 次（33%）   ← 这些都不是落子本体，是被它带出来的
     其中 2 代以上      3 次（13%）
场上老水果被这一手推动 152/1969（8%），其中被推超过 15px 的 39 颗
```

`tools/impact-story.mjs` 还能打印单手的完整时间线，比如这一手（往 x=350.8 丢一颗**葡萄**）：

```
t=0.67s  樱桃   合成  ← 直接和刚落下的那颗合成
t=0.67s  橘子   合成  ← 连锁！第 1 代
t=0.68s  柠檬   合成  ← 连锁！第 2 代
t=0.70s  猕猴桃 合成  ← 连锁！第 3 代
一手葡萄 → 30 毫秒内四连合成，净得 20 分
```

**② 合成时的「爆裂」会不会把周围击退？**
**这个游戏里没有击退。** 把 game.js 里所有会改写速度的位置全列出来只有 6 处：

| 位置 | 干了什么 | 我们的移植 |
| --- | --- | --- |
| `b.vy += GRAVITY * dt` | 重力 | ✅ 一样 |
| `b.vx/vy = dx/dt` | PBD 位置反推速度 | ✅ 一样 |
| 墙面反弹冲量（2 处） | 撞墙弹性 | ✅ 一样 |
| 球球反弹冲量（2 处） | 弹性碰撞 | ✅ 一样 |
| `drawEffects` 里的 `p.vy += 1400*dt` | **粒子**自己的重力（粒子不参与碰撞，纯视觉） | ❌ 不移植（不影响物理） |

`burst()` 只往 `state.particles` 里塞粒子，粒子不碰水果；`flash` 只是全屏白光。
所以「爆裂」在物理上是零 —— 实测也印证：**合成那一帧，150px 外水果的速度突变次数 = 0**
（真有冲击波的话这个数会很大）。

但合成的**真实物理后果**一条不落，全部算进去了：

1. 两颗本体消失 → 那一块空间瞬间空出来，上面的水果会塌下去 / 滚下来（这是后期连锁的主要来源）；
2. 新水果在**中点**生成，速度和为父辈平均，并且**额外获得 −60 px/s 的上抛初速**
   （`makeBall(mx, my, nt, (a.vx+b.vx)*0.5, (a.vy+b.vy)*0.5 - 60)`）—— 这一下「顶出去」就是会撞动邻居的；
3. 两只神奶蛙对撞时有 **130ms 全场定格**（`state.freeze`），连冷却计时都停 —— 移植版同样实现了。

换句话说：**没有爆裂击退这回事，但「被顶开、被腾空间」这类真实影响，一条都没漏。**
另外，因为移植引擎有「逐帧零偏差」回归测试，万一作者哪天真的加了击退冲量，
`node tools/verify-engine.mjs` 会立刻报出差异，不会悄悄算错。

### 3.8 为什么这一套能赢过「贪心」

推演本身只回答「这一手之后盘面长什么样」，真正决定上限的是评估函数：
它会为了**给下一颗水果留位置**而去做一些当下不加分的手（保持平整、别把同级水果埋掉、
别把小水果压在下面、别把两只大果分开）。`tools/tune.mjs` 就是验证这些值不值得的对照实验工具。

## 五、性能优化：深模式思考时间砍掉 3.5 倍，精度一点没动

要求是「**不改变精确度的前提下，把深度搜索的思考时间至少砍一半**」。
所以只做**等价加速**：数值逐位相同、决策逐位相同，只是算得更快。

### 5.1 先量清楚（不要猜）

| 量了什么 | 结果 |
| --- | --- |
| 一次 deep 决策 | **13.1 秒**，物理帧 32281 次 |
| 静止盘面单帧 | 91 µs |
| **活跃盘面单帧** | **422 µs（4.6x）** ← 推演里用的是这个 |
| 结论 | 32281 × 422µs ≈ 13.5s → **物理占了 ~100%**，GC 只占 1.5% |

CPU profiler 再往里切：时间几乎全在 `stepPhysics` 里的「球球判定」内层循环（约 40%）
和 `syncParts`（约 10%）—— 都是必须逐对小圆算的量，**不能近似**。

### 5.2 三项「数学等价」的内核优化（合计 1.18x）

1. **cos/sin 缓存**：水果角度一帧只在「速度推导」那一步变，其余时间 `Math.cos(同一个角度)` 被重复算了成百上千次。缓存后数值完全一样。
2. **接触表改扁平数组**：每个接触点原来都 `new` 一个对象，活跃盘面一帧上百个。
3. **墙判定早退**：真实外接圆都够不着墙的水果，直接跳过 16 个小圆的逐项判定。

> ⚠️ 这里踩了个大坑：`shapes.json` 里的 `rb`（包围圆半径）是**三位小数**，
> 11 个等级里有 7 个其实**略小于**真实外接半径（差 ~0.1px）。
> 游戏自己的粗筛也用这个偏小的 rb（必须照抄才能逐帧一致），
> 但「早退」这种新加的判断**必须用真实值**，否则会漏掉贴墙的推力。
> 第一版就栽在这上面：`verify-engine` 立刻报出第 215 帧开始分歧（最大偏差 526px），
> 改用 `pack()` 里算出的真实外接半径 `rbe` 后恢复 **0.00e+0**。
> —— 这也是为什么这个项目一直留着「逐帧零偏差」回归测试。

### 5.3 真正的加速来自并行：同样的计算，摊到多个 Worker

四个搜索阶段（粗筛 / 精选 / 第二层连手棋 / 细化）内部**每个候选落点互相独立**，
所以整条管线可以切片并行 —— 数值一个都不会变。

实测（同一盘面、同一套 deep 参数、浏览器里现跑）：

| Worker 数 | 决策耗时 | 加速比 | 落点是否一致 |
| --- | --- | --- | --- |
| 1 | 4857 ms | 1.00x | — |
| 2 | 3037 ms | 1.60x | ✅ |
| **4** | **2069 ms** | **2.35x** | ✅ |
| 6 | 1569 ms | 3.10x | ✅ |
| **8** | **1379 ms** | **3.52x** | ✅ |

（本机 `hardwareConcurrency = 24`；默认用 `min(6, 核数-2)`，浏览器里实测 deep 模式
**1273 ms 一手**，页面依旧 8.05 ms/帧。）

**精度保证有两道测试守着**：

- `node tools/verify-parallel.mjs` —— 并行版 vs 顺序版逐盘面对答案（落点与评估值完全一致）
- `veriy-engine.mjs` —— 移植引擎 vs 线上游戏逐帧对答案（0.00e+0 px）

> 踩坑记录：测试脚手架必须**独占时钟**。页面上还开着 demo 时，
> 游戏自己的 rAF 主循环会和测试的手动步进打架，一度看起来像「移植引擎坏了」，
> 其实是两条时间线在抢同一个 state。

## 六、成绩

都是在 **Edge headless 打开真实游戏页**（本地离线副本，与线上同一份文件）里跑出来的，
分数就是游戏自己结算的那个分数，截图见 `out/`。

| 场景 | 权重 | 分数 | 投放次数 | 最大水果 | 复活 | 平均决策 | 备注 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **最终配置 · 完整一局** | `bump=0, adj=2.4` | **4357** | 485 | **神奶蛙（第 11 级）** | 2 | 1917 ms | `out/shot-final-A2-game1.png` |
| 同样的搜索 · 换回默认权重 | 默认 | 2745 | 340 | 半奶蛙 | 1 | 1489 ms | `out/shot-final-C-game1.png` |
| 强配置 · 被 15 分钟上限截断 | `bump=0, adj=2.4` | 3306（还在打） | 371 | — | — | ~2400 ms | 说明上限远不止 3300 |
| 轻配置 · 完整一局 | 默认 | 2111 | 269 | 半奶蛙 | 1 | 726 ms | 决策更便宜、明显更弱 |
| 线上页面 · 实时模式 · 150 秒 | `bump=0` | 831（截断） | 102 | — | — | ~900 ms | `out/snap-livedemo2-*.png`，证明能直接打线上 |

两个结论：

1. **搜索深度值钱**：轻配置（step=10, h1=0.9, h2=1.8, topK=4, lookahead=1）平均 726 ms 一手 → 2111 分；
   最终配置（step=8, h1=1.2, h2=2.6, topK=8, lookahead=2 + 已知下一颗）平均 1917 ms 一手 → 4357 分。
   快进模式下 bot 可以慢慢想，这是它比人强的主要原因。
2. **权重小改也值钱**：同样搜索下 `bump=0, adj=2.4` 是 4357，默认权重是 2745。
   （单局对比方差很大，但这个方向与下面 10 局对照实验的结论一致，两条证据互相印证。）

> 4357 分那一局用的就是 `src/` 现在的默认参数 —— 直接 `NaiwaBot.run()` 即是这套配置，不用额外传参。

### 权重对照实验（10 局 × 固定 140 手预算，随机种子配对）

`node tools/tune.mjs --configs out/configs-ablation.json --games 10 --workers 8`

| 配置 | 平均分 | 中位 | 最低 | 最高 |
| --- | --- | --- | --- | --- |
| 去掉表面起伏 `bump` | **1236.8** | 1244 | 1121 | 1311 |
| 加强同级相邻 `adj=2.4` | 1187.8 | 1234 | 1037 | 1308 |
| 去掉被埋惩罚 `buried` | 1177.4 | 1192 | 1101 | 1248 |
| 纯贪心（只剩分数+越线风险） | 1172.9 | 1215 | 1028 | 1299 |
| 去掉同级相邻 `adj` | 1144.9 | 1153 | 1023 | 1280 |
| 加强合成权重 | 1129.8 | 1193 | 872 | 1223 |
| 默认权重 | 1114.3 | 1198 | 681 | 1290 |
| 加强顶部风险 `top=4` | 1097.4 | 1119 | 681 | 1290 |

样本量只有 10 局，差距在噪声范围里（±10%），所以结论要谨慎：**没有任何单项权重是决定性的**。

### 后期「大果抱团」特征的效果（10 局 × 260 手预算）

`node tools/tune.mjs --configs out/configs-late.json --games 10 --workers 8 --tune "step=14,h1=0.7,h2=1.4,topK=3,lookahead=1"`

| 配置 | 平均分 | 中位 | 最低 | 最高 |
| --- | --- | --- | --- | --- |
| **开 `bigPair` + `blocked`** | **1997.4** | 2137 | 901 | 2551 |
| 关掉这两个特征 | 1750.5 | 2075 | 724 | 2435 |

把预算拉到 260 手（这时盘面上才真的会出现两只同级大果）之后，新特征的 **平均分 +14%**；
而在 120 手的短预算上两者几乎打平（1052 vs 1000）—— 说明它治的确实是「后期病」，前期不干扰。

### 一个被否掉的假设：加强「碎果惩罚」

观察到一局结束时盘面被大量小水果挤满，怀疑是碎块惩罚太弱，于是做了 x4 / x8 的对照：

| 配置 | 平均分（8 局 × 260 手） |
| --- | --- |
| 原样 | **1915.4** |
| 碎果惩罚 ×4 | 1904.8 |
| 碎果惩罚 ×8 | 1886.0 |

结论：**没用，甚至略差**，所以没有改进默认权重（负结果也是结果，记在这里免得以后重复试）。

## 七、踩过的坑（都写进了回归测试）

1. **权重表只写部分键 → 全盘 NaN。** `planner` 现在强制与默认权重合并；
   否则 `evaluate()` 会返回 `undefined`，最后在 `toFixed` 上崩掉（真在跑分时崩过一局）。
2. **「等盘面静止再出手」不能无限等。** 物理引擎偶尔会让盘面一直微微抖，
   bot 就会卡在那里再也不出手（一次跑分卡在第 426 手）；
   现在最多等 1.5 秒游戏时间就照常出手。
3. **近似物理用来筛选落点完全不可行。** 见 3.1 的对照实验，ρ≈0。
4. **游戏结算会自动提交排行榜。** 不拦的话，跑一局就往公开榜发一条。
5. **盘面越大决策越贵**（物理是 O(n²)），后期一手要 2 秒以上；
   所以 planner 有硬预算，到点就降级搜索而不是卡死。

## 八、说明

- bot 走的是游戏**自己的输入通道**（往棋盘派发真实的 `pointerdown` 事件），
  用的是游戏**自己的物理**（推演用移植副本，真实对局仍是原版引擎），
  只是把「人看着盘面选落点」换成了「推演 45 个落点选一个」。
- 排行榜提交默认被拦下。要拿这个 bot 去刷公开榜，请自己判断合不合适。
- 引擎依赖 `window.__DNW__`（游戏自带的调试句柄）。作者如果删掉它，bot 需要改成读画布像素。
