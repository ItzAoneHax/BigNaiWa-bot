# 合成大奶娃 · AI 自动打（BigNaiWa Bot）

给 [合成大奶娃 v1](https://yhsome.github.io/BigNaiWa/v1/) 写的一个自动打手：
**把游戏的物理引擎 1:1 移植出来当年仿真模型**，每次出手前把 40+ 个落点各推演一遍，
按「拿到的分 + 盘面风险 + 后续合成机会」挑一个最稳的落点丢下去。

- 移植引擎与线上物理**逐帧零偏差**（`tools/verify-engine.mjs`：1620 帧 / 53 次投放，最大坐标偏差 0.00e+0 px，分数与球数完全一致）
- 决策管线：候选生成 → 精确推演 → 特征评估 → 精选长推演 → 两层搜索（下一颗水果是已知的）→ 局部细化
- **推演跑在 Web Worker 里**，主线程实测 8.3 ms/帧 —— 页面完全不卡（v1 是同步算，会僵住）
- 页面右上角（可拖动）有**灵动岛控制台**：暂停 / 实时·快进 / 排行榜开关 / 自动复活 / 搜索强度
- 一局打完**点重开它会自己接着打**；关闭脚本会把游戏交还给你，页面照常能玩
- 实测：浏览器里全自动单局 **4357 分**，合出最大的「神奶蛙」，用了 2 枚复活币（详见「成绩」一节）

## 一、怎么用

### 1. 最简单：控制台粘贴

1. 打开 <https://yhsome.github.io/BigNaiWa/v1/>
2. F12 → Console → 粘贴 [`dist/naiwa-bot.js`](dist/naiwa-bot.js) 的全部内容 → 回车
3. 开打：

```js
NaiwaBot.run()                                  // 实时模式：跟着游戏节奏打，可以边看边玩
NaiwaBot.run({ mode: 'turbo' })                 // 快进模式：自己驱动时钟，刷分快得多
NaiwaBot.run({ strength: 'deep' })              // 想更强就加搜索深度（fast / normal / deep）
```

开起来之后，右上角那颗小胶囊（🍉 分数 + 状态灯）就是控制台：**点一下展开**，
里面能暂停、切模式、切搜索强度、改「投掷时机」策略、开关排行榜提交与自动复活。
胶囊可以**拖着换位置**。

常用命令：

```js
const b = window.__NAIWA_BOT__;
b.stop()                     // 关掉 AI（游戏交回给你，页面照常能玩）
b.setPaused(true)            // 暂停（连游戏一起冻住）
b.setMode('turbo')           // 运行时切模式
b.restartGame()              // 重开一局，AI 继续
b.stats                      // 分数、决策耗时、投掷时机分布…
```

安装 [`dist/naiwa-bot.user.js`](dist/naiwa-bot.user.js)，打开游戏页会看到 `[合成大奶娃 bot] 已装载`，
然后在控制台敲 `NaiwaBot.run()` 即可（脚本里默认不自动开打）。

## 三、算法

### 3.1 核心：用游戏自己的物理做「假设落点」推演

最朴素的高分打法就是「丢下去之前先想一下」。难点在于**想得准**：

1. `src/engine.js` 把 game.js 里的 `stepPhysics / processMerges / checkGameOver / update / tryDrop`
   逐行照抄（同样的常量、同样的运算顺序、同样的 `Float32Array` 精度），只砍掉粒子、音效、DOM。
2. 把当前盘面搬进移植引擎（`adoptFromGame`），对每个候选落点：克隆世界 → 投放 → 固定步长跑到稳定。
3. 「克隆世界 + 跑物理」不碰真实游戏，所以推演多少遍都不影响正在进行的对局。

**保真度**：`tools/verify-engine.mjs` 在同一个浏览器进程里先跑真实游戏 1200 帧、
再用移植引擎重放同样 1200 帧，逐帧比对每颗水果的坐标 —— 结果 dx=dy=0.00e+0、分数与球数完全一致。

> 为什么不用「便宜的近似模型」来加速？`tools/model-agreement.mjs` 做了对照实验：
> 把 16 个小圆砍成 8/4/2 个、或者直接退化成圆，推演快了 20–50 倍，
> 但**排序和精确物理几乎不相关**（Spearman ρ≈0，top1 命中率 0–13%）。
> 原因是「这颗到底会不会碰到、会不会合」本来就是混沌的，模型一糙，预测就变成噪声。
> 结论：决策必须用精确物理，加速只能从「少推几次」「推短一点」「多核并行」上找。

### 3.2 决策管线（`src/planner.js`）

```
① 候选生成   可投范围 [WALL+r, W-WALL-r] 内按 step=8px 均分 ≈ 45 个落点
② 粗筛推演   每个候选投放后跑 1.2s（提前稳定就收工），算评估值
③ 精选       前 8 名再跑 2.6s 长推演（有些连锁合成要 1.5s 后才发生）
④ 期望搜索   下一颗水果是随机的：前 3 名 × {5 种可能水果} × 各自最优应对，按掉落权重取期望
⑤ 局部细化   冠军落点左右 ±8px 再试 4 个更细的位置
```

### 3.3 评估函数

推演结束后的盘面用一组归一化特征打分（权重可调、可用 `tools/tune.mjs` 做对照实验）：

| 特征 | 含义 | 方向 |
| --- | --- | --- |
| `merge` / `mergeW` | 推演窗口内真实拿到的分 / 合出的最大等级 | ＋ |
| `top` | 堆顶逼近警戒线的二次惩罚 | － |
| `above` | 越线水果数量 × 体积 | － |
| `overT` | 越线计时（离判负还有多远） | － |
| `bump` | 表面起伏（8 条竖条的顶高差） | － |
| `adj` | 同级相邻度（距离越近越可能马上合） | ＋ |
| `bigPair` | **同级大果抱团**：两只半奶蛙/神奶蛙挨着 → 大赚，分居两地 → 重罚 | ＋ |
| `blocked` | **两只大果之间塞着别的水果**（合不拢的直接原因） | － |
| `mono` | 层级沿水平方向的梯度（大果归边，默认关，可调参开） | ＋ |
| `bigHigh` | 大果被顶到高处 | － |
| `buried` | 大果压在小果上（被埋的小果就废了） | － |
| `frag` | 碎块惩罚 | － |
| `dead` | 推演中判负（手里没币时一票否决） | — |

### 3.4 投掷时机：现在丢，还是等这一波合成安静下来再丢？

> ⚠️ **2026-10-13 审计结论**：本节描述的时机比较只在 `plan()` 里实现，而浏览器里 bot 走的是 `planParallel()`（有 Worker 时），**那条路径没有时机逻辑**，所有落子都记为「立刻」（实测 185/185、292/292）。自我对弈协议又会在每手前先等盘面安静，因此时机分支从未被评估过（15/15 手都是 `quiet`）。详见第九节。

这是用户提的真问题：合成的一瞬间棋盘是乱的（水果在弹、在滚、连锁还没走完）。

现在的做法是**把时机也交给搜索**。盘面还在动的时候，规划器会算两遍、拿同一个评估函数比：

```
① 现在丢   从当前（还在动的）盘面推演 → 最优落点 a 的价值 V_now
② 等它安静 让棋盘自己跑到静止（最多 3 秒），再推演 → 最优落点 b 的价值 V_later
           （等待期间自己合出来的分也算进 V_later）
选 V 更高的那个；等待还有一点点「时间惩罚」用来打破平局。
如果光等着就输了（越线判负），直接选①。
```

推演里「丢进混乱中会发生什么」是能算准的 —— 因为那正是线上物理本身，
所以 bot 甚至能借势把水果撞进旁边的空档；这一点人类玩家做不到。

### 3.5 把复活币当资源花（用户明确要求）

复活币 = 每 2000 分一枚 + 两只神奶蛙相撞再送一枚。用户说「分越高越好，允许用币换空间」，
所以：

- **推演里允许用币续命**：一条路线如果半路越线，但手里有币，推演不会判它死，
  而是就地做一次复活（清掉警戒线以上、删掉最顶上那颗）再继续跑到底 ——
  于是「堆到顶→清一片→接着合」这种打法会被算成一笔有代价但可接受的买卖。
- **风险项缩放**：手里有币时，`top`/`above`/`overT` 这几个风险权重 × 0.45，
  允许把场面堆得更高，换取更大的合成空间。
- 灵动岛里可以一键切成「不用复活币」，自己对比两种打法。

### 3.6 后期「大果永远合不到一起」的专项治理

后期最常见的死法不是被顶死，而是**两只大奶蛙各占一边、中间塞着一堆小果**，
谁也动不了谁，最后只能在上面继续堆到爆。为此加了两项特征：

- `bigPair`：同级大果之间的距离打分（权重随 tier 超线性增长 `(tier-3)^1.6`），
  挨着 = 马上能合 = 大赚；分居两侧 = 基本等于废了 = 重罚。
- `blocked`：两只同级大果的**水平连线之间**、位置更高的水果，就是挡住它们的东西，按 tier 加权扣分。

效果就是 bot 会更愿意「先在大果旁边腾出位置、把小果往别处丢」，而不是随便找个浅坑就丢。

### 3.7 推演里到底算了什么？（以及游戏里根本不存在的东西）

两个常见疑问，这里用代码 + 实测数据回答：

**① 落下的这颗对场上其它水果的影响，算了吗？**
算了 —— 而且不是「估算」，是把**线上同一套物理**整段往前推：落子会和每一颗水果真实碰撞、推挤、滚动，
被推动的水果又可能触发别处的合成。所有候选落点的评分都来自这个前推结果。
实测（`tools/impact-probe.mjs`，4 个中后期盘面 × 89 个候选落点）：

```
落子一共触发合成 24 次
  · 落子本体直接合成  16 次（67%）
  · 连锁合成(gen>=1)   8 次（33%）   ← 这些都不是落子本体，是被它带出来的
     其中 2 代以上      3 次（13%）
场上老水果被这一手推动 152/1969（8%），其中被推超过 15px 的 39 颗
```

`tools/impact-story.mjs` 还能打印单手的完整时间线，比如这一手（往 x=350.8 丢一颗**葡萄**）：

```
t=0.67s  樱桃   合成  ← 直接和刚落下的那颗合成
t=0.67s  橘子   合成  ← 连锁！第 1 代
t=0.68s  柠檬   合成  ← 连锁！第 2 代
t=0.70s  猕猴桃 合成  ← 连锁！第 3 代
一手葡萄 → 30 毫秒内四连合成，净得 20 分
```

**② 合成时的「爆裂」会不会把周围击退？**
**这个游戏里没有击退。** 把 game.js 里所有会改写速度的位置全列出来只有 6 处：

| 位置 | 干了什么 | 我们的移植 |
| --- | --- | --- |
| `b.vy += GRAVITY * dt` | 重力 | ✅ 一样 |
| `b.vx/vy = dx/dt` | PBD 位置反推速度 | ✅ 一样 |
| 墙面反弹冲量（2 处） | 撞墙弹性 | ✅ 一样 |
| 球球反弹冲量（2 处） | 弹性碰撞 | ✅ 一样 |
| `drawEffects` 里的 `p.vy += 1400*dt` | **粒子**自己的重力（粒子不参与碰撞，纯视觉） | ❌ 不移植（不影响物理） |

`burst()` 只往 `state.particles` 里塞粒子，粒子不碰水果；`flash` 只是全屏白光。
所以「爆裂」在物理上是零 —— 实测也印证：**合成那一帧，150px 外水果的速度突变次数 = 0**
（真有冲击波的话这个数会很大）。

但合成的**真实物理后果**一条不落，全部算进去了：

1. 两颗本体消失 → 那一块空间瞬间空出来，上面的水果会塌下去 / 滚下来（这是后期连锁的主要来源）；
2. 新水果在**中点**生成，速度和为父辈平均，并且**额外获得 −60 px/s 的上抛初速**
   （`makeBall(mx, my, nt, (a.vx+b.vx)*0.5, (a.vy+b.vy)*0.5 - 60)`）—— 这一下「顶出去」就是会撞动邻居的；
3. 两只神奶蛙对撞时有 **130ms 全场定格**（`state.freeze`），连冷却计时都停 —— 移植版同样实现了。

换句话说：**没有爆裂击退这回事，但「被顶开、被腾空间」这类真实影响，一条都没漏。**
另外，因为移植引擎有「逐帧零偏差」回归测试，万一作者哪天真的加了击退冲量，
`node tools/verify-engine.mjs` 会立刻报出差异，不会悄悄算错。

### 3.8 为什么这一套能赢过「贪心」

推演本身只回答「这一手之后盘面长什么样」，真正决定上限的是评估函数：
它会为了**给下一颗水果留位置**而去做一些当下不加分的手（保持平整、别把同级水果埋掉、
别把小水果压在下面、别把两只大果分开）。`tools/tune.mjs` 就是验证这些值不值得的对照实验工具。

## 五、性能优化：深模式思考时间砍掉 3.5 倍，精度一点没动

要求是「**不改变精确度的前提下，把深度搜索的思考时间至少砍一半**」。
所以只做**等价加速**：数值逐位相同、决策逐位相同，只是算得更快。

### 5.1 先量清楚（不要猜）

| 量了什么 | 结果 |
| --- | --- |
| 一次 deep 决策 | **13.1 秒**，物理帧 32281 次 |
| 静止盘面单帧 | 91 µs |
| **活跃盘面单帧** | **422 µs（4.6x）** ← 推演里用的是这个 |
| 结论 | 32281 × 422µs ≈ 13.5s → **物理占了 ~100%**，GC 只占 1.5% |

CPU profiler 再往里切：时间几乎全在 `stepPhysics` 里的「球球判定」内层循环（约 40%）
和 `syncParts`（约 10%）—— 都是必须逐对小圆算的量，**不能近似**。

### 5.2 三项「数学等价」的内核优化（合计 1.18x）

1. **cos/sin 缓存**：水果角度一帧只在「速度推导」那一步变，其余时间 `Math.cos(同一个角度)` 被重复算了成百上千次。缓存后数值完全一样。
2. **接触表改扁平数组**：每个接触点原来都 `new` 一个对象，活跃盘面一帧上百个。
3. **墙判定早退**：真实外接圆都够不着墙的水果，直接跳过 16 个小圆的逐项判定。

> ⚠️ 这里踩了个大坑：`shapes.json` 里的 `rb`（包围圆半径）是**三位小数**，
> 11 个等级里有 7 个其实**略小于**真实外接半径（差 ~0.1px）。
> 游戏自己的粗筛也用这个偏小的 rb（必须照抄才能逐帧一致），
> 但「早退」这种新加的判断**必须用真实值**，否则会漏掉贴墙的推力。
> 第一版就栽在这上面：`verify-engine` 立刻报出第 215 帧开始分歧（最大偏差 526px），
> 改用 `pack()` 里算出的真实外接半径 `rbe` 后恢复 **0.00e+0**。
> —— 这也是为什么这个项目一直留着「逐帧零偏差」回归测试。

### 5.3 真正的加速来自并行：同样的计算，摊到多个 Worker

四个搜索阶段（粗筛 / 精选 / 第二层连手棋 / 细化）内部**每个候选落点互相独立**，
所以整条管线可以切片并行 —— 数值一个都不会变。

实测（同一盘面、同一套 deep 参数、浏览器里现跑）：

| Worker 数 | 决策耗时 | 加速比 | 落点是否一致 |
| --- | --- | --- | --- |
| 1 | 4857 ms | 1.00x | — |
| 2 | 3037 ms | 1.60x | ✅ |
| **4** | **2069 ms** | **2.35x** | ✅ |

## 七、踩过的坑（都写进了回归测试）

1. **权重表只写部分键 → 全盘 NaN。** `planner` 现在强制与默认权重合并；
   否则 `evaluate()` 会返回 `undefined`，最后在 `toFixed` 上崩掉（真在跑分时崩过一局）。
2. **「等盘面静止再出手」不能无限等。** 物理引擎偶尔会让盘面一直微微抖，
   bot 就会卡在那里再也不出手（一次跑分卡在第 426 手）；
   现在最多等 1.5 秒游戏时间就照常出手。
3. **近似物理用来筛选落点完全不可行。** 见 3.1 的对照实验，ρ≈0。
4. **游戏结算会自动提交排行榜。** 不拦的话，跑一局就往公开榜发一条。
5. **盘面越大决策越贵**（物理是 O(n²)），后期一手要 2 秒以上；
   所以 planner 有硬预算，到点就降级搜索而不是卡死。

## 八、说明

- bot 走的是游戏**自己的输入通道**（往棋盘派发真实的 `pointerdown` 事件），
  用的是游戏**自己的物理**（推演用移植副本，真实对局仍是原版引擎），
  只是把「人看着盘面选落点」换成了「推演 45 个落点选一个」。
- 排行榜提交默认被拦下。要拿这个 bot 去刷公开榜，请自己判断合不合适。
- 引擎依赖 `window.__DNW__`（游戏自带的调试句柄）。作者如果删掉它，bot 需要改成读画布像素。

### 9.2 精确性保证（新增工具）

- `tools/ref/`：优化前 `engine.js` / `planner.js` 的冻结副本，作为金标准。
- `tools/verify-exact.mjs`：逐位（`Object.is`）对拍。引擎逐帧比较所有字段，含随机投放、复活、神奶蛙对撞用例、中途 clone 续跑；规划器比较顺序版与并行版（1/3/7 片切分）的落点、评估值、候选排名与时机选择。最终结果：比较点 45440，差异 0。
- `tools/verify-engine.mjs`（浏览器，对线上游戏）：3/3 轮 0.00e+0 px。
- `tools/verify-inpage.js` 时钟修复：游戏的 `landed` 判定用墙钟 `performance.now()`，而移植端用虚拟时钟；手动步进时墙钟流逝快慢不定，第一轮 JIT 未热时两边的越线判负会在不同帧发生，于是投放序列分叉。校验期间改为虚拟时钟同步推进（推进量与 `update()` 相同），修复后 3/3 轮完全一致。这是**校验脚本的缺陷，不是引擎偏差**。

### 9.3 策略审计

1. **投掷时机在并行路径里不生效**（见 3.4 的警告）。这是一个真实的功能缺口，HUD 里的「投掷时机」开关在浏览器里不起作用。两个选项：把 `timing` 逻辑移植进 `planParallel`（代价：每手要多跑一次完整推演，且仅在盘面运动时才需要），或者从 UI 中移除该开关。在没有数据之前不建议直接启用。
2. **自我对弈协议与线上不一致**：`selfplay.mjs` 每手前等盘面安静（`maxSpeed ≤ 60`），线上 bot 则在冷却结束时立即出手。因此 `tune.mjs` 得出的权重结论没有覆盖时机问题，也没有覆盖「盘面还在抖时出手」的情况。建议新增一个「不等安静」的对弈模式后重测。
3. **得分经济（来自 `game.js` 的数值）**：每颗水果携带 `2^tier` 个「代币」，合成守恒代币，复活会删掉水果、神奶蛙对撞会销毁 2048 个代币。每次投放的期望代币为 0.28·1 + 0.24·2 + 0.20·4 + 0.16·8 + 0.12·16 = **4.76**。合成得分是三角数，把一整棵树合成完约 3.6 分/代币，因此「每次投放的理论上限」约 17 分。线上实测约 9.4 分/投放，即**大约一半的代币没有兑现**。同时两颗神奶蛙相撞一次约需 430 次投放的代币，所以 500 分奖励本身很稀有，主要收益来自存活时间与合成效率。
4. **评估函数缺少「材料」项**：复活删掉的水果、堆在盘面上尚未合成的代币，目前都没有被计入。新增可选项 `mat`（默认关闭，缺省时完全不参与计算，`verify-exact` 仍然全部一致）。实验（8 局配对种子，每局 150 手，normal 档）：基线平均 1315.6，`mat=1.0` 平均 1333.3（+1.3%）。**差值远小于 8 局的标准误，结论是「未见效果」**，因此保持关闭。若要真正检验，需要更多局数（约 40 局以上）并结合上面第 2 条的对弈协议。
5. **负结果**：同前（见第六节「碎果惩罚」），本轮未再提出能让人信服的新权重方向。

## 十、挤压抖动 / 底部大果 / 结果复用（2026-10-13 第二轮）

用户的三个反馈：① 奶蛙被挤住上下抖动时思考特别慢；② 光消顶部只是拿分，底部那一堆合不掉的奶蛙才是长久的病；③ 上一步的模拟结果应该能复用给下一步。这一轮把三个都量了一遍。

### 10.1 「抖动」到底慢在哪（结论和直觉不一样）

用 `tools/jitter-probe.mjs` 造出「底部挤满大果」的盘面，`tools/jitter-diag.mjs` 逐窗口打印，
`tools/dense-profile.mjs` 做 CPU 剖面。实测：

| 量 | 结果 |
| --- | --- |
| 抖动时每帧最大速度 | 一直在 30~200 px/s 之间尖峰（所以 `runSettle` 的「速度 < 25」永远不触发） |
| 但每 16 帧的**整盘净位移** | 只剩 0.5~1.2px —— 盘面其实**已经不动了** |
| 密集盘面单帧成本 | 26 颗时 **105 µs**（18 颗时 73 µs）；物理 96% 的时间都在 `stepPhysics` |
| 一次决策的物理帧数 | 密集盘面 **23050 帧**（18 颗盘面 17613 帧，+31%） |
| 帧数去向 | 第二层内层搜索占 **60~76%**（244 个推演 × 72 帧） |
| 窄相位里真正需要 `Math.sqrt` 的比例 | 每帧约 2600 个小圆对扫描里只有 45 对真的重叠 → 推迟 sqrt 只值 ~1%，不做 |

结论：**「抖动」本身不是浪费时间的主因**。盘面被砸一下之后确实要 1.3 秒才重新静下来
（那是真物理，不是空转），所以推演跑满时间窗基本是应该的；真正让思考变慢的是
「密集盘面 → 单帧成本 ×1.4」×「不早退 → 帧数 +31%」×「一次决策 244 个推演」。

本轮为此做了两件事：

1. **加了第二条收工规则**（`SETTLE`，`tools/settle-ab.mjs` 验证）：不只看瞬时速度，
   还看**整盘净位移** —— 连续两个 16 帧窗口里每颗水果位移 < 1.5px 才算冻住。
   物理一个比特没动，只改「什么时候收工」。
   实测：省 1~3% 的物理帧，但 **5 个盘面里有 1 个换了落点**。
   按本项目「决定不同就必须有证据证明更好」的规矩，**默认关闭**；想在抖动盘面上再快一点：
   ```js
   NaiwaBot.planner.SETTLE.vibrate = true     // 打开第二条收工规则
   ```
2. 真正的加速仍然来自前面几轮：引擎 4.3 倍、Worker 默认 12 个（`min(12, 核数-4)`）。
   端到端实测（Edge headless、快进、同一台机器）：

| 版本 | Worker | 平均决策 | 90~120 秒内投放 |
| --- | --- | --- | --- |
| 本轮之前（旧 dist） | 6 | **637 ms** | 185 次 / 120 秒 |
| 本轮之后 | 12 | **255 ms** | 343 次 / 90 秒 |

> 也就是说：**要看效果必须先重新粘贴新的 `dist/naiwa-bot.js`**（旧脚本留在页面里不会自动升级）。

### 10.2 底部「无效大果」：机制做了，但证据不支持开

按用户的观察加了两项（默认关闭，权重缺省时完全不参与计算）：

| 特征 | 含义 |
| --- | --- |
| `stuck` | 没有同级伙伴的大果（2.5 倍半径和之内都没有）—— 占着地方又合不掉，按面积 (r/100)² 计权 |
| `space` | 这一手合成**净释放**的面积（两颗消失、一颗更大的顶上）—— 大果收益随半径平方增长 |

注意一个机制约束：新水果只掉 0~4 级，**大果只能靠合成攒出来**，所以「底部那堆奶蛙」在
当前这一手是无法直接补救的（最多是别再添乱、并腾出空间让它们有机会靠拢）。
这解释了下面的实测结果。

证据（`tools/tune.mjs`，配对种子）：

| 配置 | 局数 | 平均 | 中位 | 最低 |
| --- | --- | --- | --- | --- |
| base | 8 | 1673.6 | 1747 | **1026** |
| stuck20 space60 | 8 | 1746.8 | 1759 | 1674 |
| stuck50 space150 | 8 | 1737.4 | 1761 | 1632 |

看起来 +4.4%，但**逐局配对看是假的**：8 局里只有 seed 5007 一局拉开差距（base 1026 → 1700+），
其余 7 局是 4 胜 4 负的噪声；而且用 `tools/weights-ab.mjs` 检查发现，
**stuck20/space60 在 6 个盘面上落点完全没变**（权重太小、是惰性的，跑分差异纯属轨迹分叉）。
把权重加大到 200/600 才偶尔改落点（6 个盘面里改 1 个）。

所以：**机制留在代码里、默认关闭**，需要时用
`NaiwaBot.run({ think: { weights: { stuck: 200, space: 600 } } })` 打开。
要真的下结论，得跑 30~50 局配对（单局方差 ±100 分以上）。

**加大权重之后跑了 16 局配对，结果是明确的负结果**（`out/tune-2026-10-13T09-53-27.json`）：

| 配置 | 局数 | 平均 | 中位 | 最低 |
| --- | --- | --- | --- | --- |
| base | 16 | **1747.9** | 1798 | 1224 |
| stuck200 space600 | 16 | 1629.1 | 1753 | **409** |

逐局配对：平均 **−118.8 分**，胜 6 负 10，其中两局直接崩到 1156 / 409。
也就是说：把「底部长远受益」加权到足以改变落点之后，**打法反而更差**。
原因与 10.2 的机制约束一致 —— 大果只能靠合成攒出来，这一手无法直接补救底部的堆积，
强行加权只会让 bot 为了眼前的一次大合成去接受更差的盘面。
（负结果也是结果，记在这里免得以后重复试。）

### 10.3 「上一步的模拟结果复用给下一步」——为什么现在复用不了

已经做到的复用（都是精确的、不影响结果）：

- 第二层的外层基准直接取精选阶段的 `v2`（两者是同一条推演：同盘面、同落点、同 h2/quiet），
  省掉每个外层一次 156 帧的重复推演；
- 顺序版里「内层盘面」与「复核盘面」共用一份缓存。

而**跨决策**复用这条路，在当前搜索结构下走不通，原因是具体可查的：

1. 第 N 步的推演算的是「假设把**没选**的果子丢在别处会怎样」——它们落在
   `(当前盘面 + 落子) 完全稳定之后` 的盘面上；
2. 第 N+1 步的真实盘面是 `(当前盘面 + 落子) 又走了 360ms 冷却` 的状态 ——
   两者**从来不是同一个状态**（前者更"未来"，后者还在晃）；
3. 而且第 N+1 步要问的是「再丢一颗会怎样」，比第 N 步的推演又多了一层。

所以拿状态指纹做命中缓存的写法会 100% miss（不是实现问题，是问题定义问题）。
真正能把这份算力留下来的改造是**把搜索做成跨手保持的树**：
把第二层那次落子的时机从「盘面完全稳定」改成「真实的下一手时刻（落子 + 360ms 冷却）」——
这个语义更接近线上实际打法；这样一来第 N 步的第二层推演**就是**第 N+1 步的第一层推演，
下一步只需要往下多展开一层，等于「用两层的代价拿到三层」。这是一次结构改造
（要跨决策保活世界状态、并且依赖时机逐帧可预测，快进模式下是严丝合缝的），
本轮没有动，列为下一步。

## 十一、「跨投掷复用预测结果」能省多少思考时间？（2026-10-13 第三轮）

用户的问法：给现在的推演模型加上「跨投掷复用」，思考时间会不会明显下降？
量它的工具：`node tools/reuse-ceiling.mjs`（两个盘面：中后期 18 颗 / 密集 26 颗，参数就是 bot 默认的 deep 档）。
**结论先说：不会，天花板只有 ~19% 的帧，而且要先做两处「会改变决策」的重构。真正值得做的动机是棋力，不是速度。**

### 11.1 一次决策的物理帧花在哪（现状，live 协议：冷却一结束就投）

| 阶段 | 单元数 | 物理帧 | 占比 | 帧/单元 | 单线程 ms |
| --- | --- | --- | --- | --- | --- |
| ① 粗筛 screen | 46 | 3284 | 14.4% | 71 | 350 |
| ② 精选 long | 8 | 1217 | 5.3% | 152 | 127 |
| ③ **第二层 inner** | 236 | **17321** | **75.8%** | 73 | 1775 |
| ④ 复核 recheck | 4 | 558 | 2.4% | 140 | 52 |

—— 与线上实测平均 255 ms 一手口径一致。）

### 11.2 「拿状态去查表」这种复用：命中 0/46，而且不是实现问题

- 第 N 步的 46 条推演**起点**都是同一个盘面（`cloneWorld`）；第 N+1 步的真实起点是
  「落子 + 22 帧（360 ms 冷却结束）」——**两者从不相等**；
- 第 N 步推演**收工**（落子后跑到稳定）的盘面 vs 第 N+1 步的真实起点：
  位移 **122 px**、速度差 **1083 px/s**（密集盘面上甚至多合了一次，球数都不一样）；
  最近的未命中条目也差 114 px —— 不是浮点误差级别的差别；
- 反过来看：**冠军轨迹 +22 帧处的状态与下一步真实起点逐位相同（0.000 px / 0.000 px/s）**。
  也就是说，正确的复用形态是「把那条轨迹留到下一手」，而不是「拿状态去查表」——
  这也正是 10.3 那条结论的量化版本。

### 11.3 就算把搜索改成跨手保活的树：天花板 ~19%，代价是两处语义改动

必须先付的两笔代价（两笔都会**改变落点**，要重新做 A/B）：

1. **第二层的落子时机**要从「盘面完全稳定」改成「真实的 360 ms 冷却」，
   否则第 N 步第二层所在的盘面 ≠ 第 N+1 步的盘面（11.2 的第一条就是这个）；
2. **候选栅格要统一**：粗筛 step=8（46 个落点）与第二层内层 step=6（59 个落点）
   **位置完全相同的落点 = 0 个**（实测）——不统一，一个都命中不了。

统一之后能省下的：

| 省掉的东西 | 帧 | 占比 | 为什么 |
| --- | --- | --- | --- |
| 粗筛整段（第 N 步的第二层 = 第 N+1 步的粗筛） | 3284 | 14.4% | 冠军那条轨迹的第二层推演，本来就是下一步的粗筛 |
| 精选的前 72 帧（从留住的盘面续跑） | 576 | 2.5% | 同一条推演，只是要跑更长 |
| 第二层的「外层盘面」（直接用冠军轨迹 +22 帧） | 593 | 2.6% | 原来每个外层都要重跑一遍稳定（156 帧） |
| **合计** | **4453** | **19.5%** | 255 ms → 约 207 ms |

**省不掉的就是大头**：第二层内层扫描占 75.8% 的帧，它问的是「下一颗水果丢哪儿」，
而下一颗水果在第 N 步**还不存在**（`tryDrop` 执行时才生成 `next`）——
那 236 个推演每次都必须重算。复用的对象只能是比较浅的那一层，这就是上限的来源。

所以：**为了省时间去改它不值当**（19% 上限 / 两个改决策的重构 / Worker 协议要变成跨手保活状态 /
快进模式之外还要处理失配回退）。但同一套改造**为了棋力是值的**：现在第二层推演跑在
「落子完全稳定之后」，而线上 turbo 是「冷却一结束就投」，两者本来就不是一回事
（第九节 9.3-1 记的正是这个时机缺口）。要做就按「让推演对齐真实出手时刻」的目标做，省下的 19% 只是副产品。

### 11.4 真正便宜的复用：同一次决策内部的前缀复用（逐位一致）

粗筛的状态留着给精选续跑、精选的外层盘面直传给第二层 —— 实测省
**4.8%（18 颗）/ 5.1%（26 颗）** 的帧，且续跑出来的盘面与从头跑**逐位相同**
（工具里 `exactBits=true`，shortlist 也完全一致）。这是唯一一条能用 `verify-exact.mjs`
当护栏的复用路线（纯重构、数值不动），只是收益也就 5%。

## 十二、从「快进」切回「实时」会卡死 —— 根因与修复（2026-10-13）

**现象**（用户报告）：快进模式下一切正常，一按「实时」整盘冻住 —— 冷却不再递减、水果不再下落，
bot 再也出不了手，看起来就是卡死。

**根因**：游戏自己的主循环是一串「自我续排」的 rAF 链：

```js
/* site/game.js */
function frame(now) { …update(FIXED)×n; render(dt); requestAnimationFrame(frame); }
requestAnimationFrame((t) => { last = t; requestAnimationFrame(frame); });
```

`frame` 是闭包，`window.__DNW__` 只暴露了 `state/reset/tryDrop/update/render` 这些，**没有暴露循环本身**。
而快进模式接管页面时钟的做法是把 `window.requestAnimationFrame` 换成 `() => 0` ——
于是游戏主循环在**下一次回调之后就断了**。`bot.setMode('realtime')` 原来只把函数还原回去，
那条链并不会自己接上：没有 `update()` 就没有冷却递减，`S.ready` 永远 false，
`requestPlan()` 再也不触发 → 从外面看就是卡死。

复现数据（同一页面，只差这一段代码）：

```
快进 3 秒（25 手）→ setMode('realtime')
  t+0.0s   10 颗，cooldown=-0.0067 ready=true    ← bot 还补投了最后一颗
  t+2.5s   11 颗；新水果停在 y=74 不掉，cooldown 卡在 0.36、ready=false 再也没变 → 卡死
```

**修复**（只动 `src/bot.js` 的驱动层）：

1. `hijackRaf()`：接管 rAF 时**把排队的回调记下来**（游戏主循环的下一环就在里面）；
2. `unhijackRaf()`：切回实时时把这些回调**重新排上**，等于把链接回游戏自己手里；
3. 一个都没记到（页面主循环本来就停着）→ 退化成 `startOwnLoop()`：用与 `game.js` 等价的
   墙钟累加 + 固定步长主循环自己推帧，照样不会冻住；
4. `stop()`（关闭脚本）走同一条路；`ownLoop` 与 turbo 的 `stepFrame` 互斥，**不会两边同时推帧**。

**验证**（线上页面实测，两条路径）：

| 场景 | 结果 |
| --- | --- |
| 页面主循环活着：turbo → realtime | 日志 `已把游戏自己的主循环接回（1 个回调）`；之后继续出手（24→31 手）；实测冷却 330~351 ms（= 360 ms 冷却，**没有双倍推帧**） |
| 页面主循环已经死了（就是上面那个卡死现场）：turbo → realtime | 日志 `页面主循环没在跑 → 由 bot 用等价主循环接管推帧`；盘面继续走（2→6 手） |

回归：`node tools/selftest.mjs` ✅、`node tools/verify-exact.mjs` ✅（11415 个比较点 0 差异）——
这次改动只在驱动层，物理一个比特都没动。

> 两个复现/排查要点（都踩过）：
> ① 必须在**全新页面**上做 —— `run()` 遇到「已在跑」的实例会**直接返回旧实例**，
> 于是你以为在测新代码，其实测的还是页面里那个老的；
> ② 判断是否卡死要看 `cooldown` 有没有递减 / 水果位置有没有变，
> **只看 `drops` 会误判**：切回瞬间 bot 还会把手里那手投出去，`drops` 会 +1 然后就不动了。
